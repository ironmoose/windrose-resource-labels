### What is in it, and how to read a sign

Source: `tools/cook-kit/engraving-test/T_PlaqueSign_01_M_diag.png`, generated by
the committed `tools/cook-kit/engraving-test/gen_diagnostic_atlas.py`.
2048x1024, mode `L`, white on black, 16 cols x 8 rows of 128px cells -- the same
geometry as the proven VT cook, so the VT-ness is not in question.

**Every cell is stamped with its own PHYSICAL address, COLUMN FIRST:**

```
"<col in hex 0-9,A-F><row 0-7>"     e.g.  "60" = physical column 6, row 0
                                          "A2" = physical column 10, row 2
```

Plus, per cell:
- a **4px border** inset from the cell edge, and
- a **solid square in the cell's TOP-LEFT corner**.

Those two are the real measuring instruments:

| What the user sees on a sign | What it means |
|---|---|
| one clean bordered box, two crisp glyphs | the material samples exactly one physical cell -- read the glyphs to get its (col,row) |
| glyphs sliced, two partial boxes side by side | horizontal cell size is wrong (material still dividing by 10 on a 2048-wide texture, or similar) |
| glyphs sliced top/bottom | vertical cell size is wrong |
| corner square appears at the **bottom**-left | UV is V-flipped |
| a whole grid of tiny numbers on one sign | the material is sampling far more than one cell |

**The key measurement.** Place a vanilla sign of a KNOWN index (Ore = index 6
per `CLAUDE.md`) and read it:

- clean **`60`** -> physical column 6, row 0. Index-decode is 10-wide as
  documented AND the material's horizontal cell size already matches the
  2048-wide (16-cell) texture. Route X geometry confirmed.
- sliced glyphs straddling **`90`/`A0`** -> the material is still using a
  horizontal cell size of 1/10 against a 2048-wide texture (u = 6/10 = 0.6 lands
  at x = 1228, i.e. column 9.6). That is the exact mis-match that garbled every
  sign last time, and it is fixable in the material, not in the atlas.
- anything else -> record the literal glyphs; the pair (col,row) directly gives
  the mapping the material actually applies.

**Row growth** (does the grid address rows 2-7?) is read the same way: whatever
mechanism can request a high index, the answer is just whichever row digit shows
up. No inference needed.

**This atlas is a measuring tool, not shippable.** Unlike the earlier test
atlas, rows 0-1 are NOT preserved vanilla art -- every cell is a number, so
every sign in the world (vanilla ones included) will read as numbers while it is
deployed. Local client only. Restore golden afterwards.

## Part 2 -- Feasibility: can we author an MI of the cooked `M_DD_PlaqueSign`?

`CLAUDE.md` asks three sub-questions. Answers:

### (2) Official R5 modkit / editor from Kraken Express: **NO**

Windrose (Early Access, April 2026) ships **no official mod support, no Steam
Workshop, and no modding tools or SDK** from Kraken Express. Modding is entirely
community-driven -- hand-built UE `.pak`/`.ucas`/`.utoc` files distributed off
Nexus. So there is no game-specific editor build that would hand us the real
source materials. That unlock is closed for now; worth re-checking if Kraken
Express announces mod support.

### (1) Can the editor load a cooked material and parent an MI to it?

Windrose is not installed here, so this was reproduced locally with an identical
setup: author a material with a `Sign Index Override` scalar, cook it, drop the
**cooked** `.uasset` + `.uexp` back into `Content/` at the same package path
(exactly what dropping in an extracted `M_DD_PlaqueSign` would look like), then
try to build an MI on it.

**Result, in order:**

1. **Plain `load_asset` fails**, and the engine names its own escape hatch:
   ```
   Unable to load package '/Game/CookProbe/M_CookProbe'. Package contains cooked
   data which is not supported by the current build. Enable 'Allow Cooked
   Content In The Editor' in Project Settings under 'Engine - Cooker' section.
   ```
   That is CVar `cook.AllowCookedDataInEditorBuilds`
   (`UCookerSettings::bAllowCookedDataInEditorBuilds`).

2. **With the CVar on, the cooked material loads fine and is introspectable:**
   ```
   OK | load_asset(cooked M_CookProbe) -> <Object '/Game/CookProbe/M_CookProbe' Class 'Material'>
   OK | get_scalar_parameter_names on cooked material -> ['Sign Index Override']
   ```

3. **An MI can be authored on it, and the override sticks and saves:**
   ```
   OK | create MI (no parent) -> <Object '.../MI_CookProbe_Test' Class 'MaterialInstanceConstant'>
   OK | set_material_instance_parent(cooked material)
   OK | read back MI parent -> <Object '/Game/CookProbe/M_CookProbe' Class 'Material'>
   OK | set scalar 'Sign Index Override' = 6.0
   OK | read back scalar -> 6.0
   OK | save MI -> True
   ```

4. **But COOKING that MI crashes the cooker.** Hard assertion, not a warning:
   ```
   Assertion failed: EditorEntry.EditorInfo.Num() == Entry.ParameterInfoSet.Num()
   [File: Engine\Source\Runtime\Engine\Private\Materials\MaterialCachedData.cpp] [Line: 766]
   ...
   LogInit: Display: Failure - 1 error(s), 4 warning(s)
   ```
   The cooked parent has no editor-only parameter info, so the cached-parameter
   bookkeeping mismatches the moment the cooker touches it. The crash killed the
   cook mid-run and **deleted the already-cooked atlas output** on its way down
   (recovered from backup, then re-cooked clean -- see "State left").

**Verdict: parenting a production MI directly to the extracted cooked material
is NOT viable on stock UE 5.6.1.** It works right up to the cook and then dies.

### The alternate route that DOES cook: a stub parent

Standard UE modding workaround, and it works here: parent the MI to a **stub**
material -- one we author ourselves in the editor, at the **same package path**,
carrying the **same parameter names** as the real one. The MI then cooks through
the completely normal path; at runtime the game resolves the import by package
path to **its own** real material, and scalar overrides bind **by name**.

Cook result with the stub parent:

```
LogInit: Display: Success - 0 error(s), 0 warning(s)
```

And the cooked MI genuinely carries what we need -- strings and bytes read back
out of the cooked files:

```
MI_CookProbe_Test.uasset -> ['/Game/CookProbe/MI_CookProbe_Test', 'EMaterialParameterAssociation',
  'MaterialInstanceBasePropertyOverrides', 'MaterialParameterInfo', 'ScalarParameterValue',
  'ScalarParameterValues', 'Sign Index Override', '/Game/CookProbe/M_CookProbe', ...]
MI_CookProbe_Test.uexp   -> contains float 6.0 bytes: True
```

Parent referenced by package path, `Sign Index Override` in
`ScalarParameterValues`, value `6.0` serialized. That is the whole payload a
per-index override MI needs.

**What this does and does not prove.** It proves the *cook* side is unblocked
and the MI serializes correctly. It does **not** prove the runtime binds our MI
to the game's real material and honours the override -- that is an in-game
question only Fedora can answer, and it is the natural content of the Step 1
test that `CLAUDE.md` already describes.

**Note for packing:** the cook emits the stub's own cooked `M_CookProbe.uasset`/
`.uexp` alongside the MI. **Ship only the MI**; the stub's cooked output must be
discarded, never packed, or it would override the game's real material with an
empty one.

### THE BIG ONE: the vanilla atlas is 1280x256 -- 10 cols x 2 rows, 20 cells

Read straight out of the extracted cooked `T_PlaqueSign_01_M.uexp`
(`FTexturePlatformData`: `SizeX=1280, SizeY=256, PF_DXT1`). At 128px cells that
is **10 columns x 2 rows = 20 cells total**.

This confirms the `1280x256` figure the cook guide asserted, and it kills the
guide's internally inconsistent "28 tiles at a 10x2 grid" (10x2 = 20).

**Why this reframes everything.** We have been overriding a **1280x256, 10x2**
texture with a **2048x1024, 16x8** one. That changes the width, the height, the
aspect ratio, the row count *and* the streaming mode all at once -- and then the
deployment garbled every sign. The prior handoff attributed the garbling to a
10-vs-16 **column** mismatch, but the vertical is a bigger change: vanilla has
**2** rows and we shipped **8**. If the material's cell size is a fixed fraction
(1/10 wide, 1/2 tall) rather than derived from the bound texture's real
dimensions, then a 2048x1024 atlas makes every "cell" sample a 204.8 x 512 px
slab -- total garble, exactly as observed.

**Consequence for the plan:** "does the grid grow to rows 2-7" is not a
side-question, it is *the* question. Vanilla has no rows 2-7 at all. All 52
production indices (20..71) live in rows that do not exist in the vanilla atlas.

### Is vanilla a virtual texture? Strong evidence for NO, not proven

The prior handoff left this open ("the guide asserts vanilla is a 1280x256
native unpadded VT; that cannot be reconciled with 5.6.1 refusing a 1280-wide
VT"). Two independent signals now point the same way:

1. **UE 5.6.1 refuses VT at 1280 wide.** Importing the vanilla-shaped source
   this session produced, verbatim:
   `LogTexture: Warning: VirtualTextureStreaming not supported for
   "T_PlaqueSign_01_M", texture size is not a power-of-2`.
   Vanilla is 1280 wide. R5 is a UE 5.6.1 fork. So vanilla almost certainly is
   **not** a VT.
2. The `bIsVirtual` field parses as `0` on the vanilla asset.

**But do not treat signal 2 as proof, and I am flagging why:** the engine
serializes a *different set of fields* in the VT and non-VT branches
(`TextureDerivedData.cpp`, `SerializePlatformData`), so fixed byte offsets are
not valid across both. As a control I ran the same parse over **our own** cooked
2048 atlas -- which the 2026-08-03 cook log reported as `TFO_AutoDXT VT` -- and
it *also* read `bIsVirtual=0`. Either that control is not really a VT, or the
parse is reading a shifted slot. I could not tell which from bytes alone, and
this project has already been burned once by byte math, so I stopped there
rather than assert. Signal 1 stands on its own regardless.

**If vanilla is not a VT, the entire 2048 power-of-two VT pivot was solving a
problem vanilla does not have** -- it converted a plain streamed texture into a
virtual one as a side effect of chasing power-of-two.

| 5 | same, with a real glyph + carved look | flat white square (identical) |

### Result #3 is the important one: the cell math does not adapt

At 2048x1024 a single sign displays the **whole** 16x8 grid at UV 0..1, rather
than one cell. So `M_DD_PlaqueSign`'s cell selection is tied to the vanilla
atlas's dimensions -- feed it a different size and the mapping collapses.

Combined with vanilla being 1280x256 (10x2, 20 cells), **"does the grid grow to
rows 2-7" is answered: no, not by swapping in a bigger atlas.** Route X as
written -- a taller atlas carrying 52 custom cells -- does not work.

Caveat kept deliberately: #1 and #3 changed *size* and *VT-ness* together, so
those two variables are still entangled. A 2048x1024 **non-VT** build was cooked
to break the tie but never got tested. It is staged and ready if anyone wants to
close that loop.

### CORRECTION 1: "vanilla is near-certainly NOT a virtual texture" -- withdraw this

Part 3 argued this from UE 5.6.1 refusing VT below power-of-two. The in-game
evidence points the other way: a non-VT override blanked every sign (#1) while a
VT override at least sampled (#3), which is what you would expect if the
material reads through a VT sampler. Vanilla's `.ubulk` also refuses to decode
as a plain BC1 mip chain, consistent with VT tile data.

**Status: genuinely unresolved.** The power-of-two rule is a fact about *our*
stock editor and does not constrain what the fork shipped. Do not plan around
either answer until it is measured directly.

### CORRECTION 2: "net-new materials render in the fork" -- WRONG, and here is the real story

When our own material was deployed, every sign changed from vanilla icons to a
flat white square. That was read as "our material is rendering". It is not --
**a flat featureless white quad is UE's default-material fallback.** The game log
says so outright:

```

  for shader platform 'PCD3D_SM6' in the shader library while serializing asset M_WRL_PlaqueEngraving
LogMaterial: Warning: Invalid shader map ID caching shaders for 'M_WRL_PlaqueEngraving',
  will use default material.
LogMaterial: Can't compile M_WRL_PlaqueEngraving with cooked content, will use default material instead

  will be used in game.
```

**The lesson worth keeping: READ `%LOCALAPPDATA%\R5\Saved\Logs\R5.log` AFTER
EVERY IN-GAME TEST.** It names the failing asset and the reason. Two rounds of
testing were spent judging by eye when the answer was sitting in the log.

### The real blocker for custom materials: the shader library name

Our material's package loads fine (`NumPackages=3` mounted, no load errors) --
only its **shaders** are missing. Cooked shaders live in
`ShaderArchive-<ProjectName>-<Platform>.ushaderbytecode`, and the game only
opens the library named after **its own** project, `R5`. Our cook project was
named `WindroseIcons`, so it shipped `ShaderArchive-WindroseIcons-*`, which
nothing ever opens.

**This also explains why the menu-icon channel worked all along: textures carry
no shaders.** The "net-new packages work if you cook them for real" rule is true
for textures and does NOT extend to materials without solving this.

**Attempted fix, cooked and packed but NOT YET TESTED:** cook from a project
literally named `R5` (`C:\R5Cook\R5.uproject`, a copy of the WindroseIcons
project). That produces `ShaderArchive-R5-PCD3D_SM6-PCD3D_SM6.ushaderbytecode`,
matching what the game opens, and drops the pak from 107 MB to 15 MB by shipping
only the R5 archives (not the engine Global ones, which would collide).

Pak built and verified at
`~/workspaces/windrose-signs/WindroseResourceLabels_OwnMaterialR5_P.*`.
**Unknown whether the game merges a same-named shader library from a mod
container with its own.** That is the next thing to find out, and the log will
say plainly.

### THE FIND: each label DataAsset names its own MaterialInstance

Extracted `DA_BI_Utilities_Lables_Wooden_Ore` and dumped its import table:

```
/Game/Environment/Shaders/InstanceMaterials/Decal/PlaqueSign/MI_DD_PlaqueSign_01   <- the MI
/Game/Environment/Gameplay/Building/BuildingDecoration/SM_WallPlaqueT02_02         <- board mesh
/Engine/BasicShapes/Plane                                                          <- engraving plane
/Game/UI/HUD/Building/Icons/BuildingBits/T_PlaqueT02_Ore                           <- menu icon
/Game/Gameplay/Building/Actors/BP_BuildingBlock_WallPlaqueT02_02
```

**The material instance is a per-DataAsset reference.** So labels do not have to
share the vanilla MI. Point each of our 52 DataAssets at its own MI, parented to
our own material, and the atlas stops mattering entirely:

| Old blocker | Under the own-material design |
|---|---|
| atlas capped at 20 cells | gone -- our textures, our sampler |
| MI-on-cooked-parent crashes the cooker | gone -- we own the parent |
| CPD04 written only by native C++ | gone -- glyph baked per MI |
| reload jank | should be gone -- no runtime CPD dependency |
| atlas dimensions load-bearing | irrelevant -- no atlas |

Design becomes: **one material with a texture parameter, 52 MIs each holding its
own glyph, 52 DataAssets each naming its MI.** No atlas, no cell index, no UV
math. Still pure-pak, so co-op/dedicated-server stays clean.

**Gated entirely on the shader-library question above.** If custom material
shaders cannot be shipped, this design dies and the mod is confined to the
game's own material and its 20 cells.

### Testing hazard, recorded

Mid-session the game reported **"Looks like parts of your save files are
broken"** -- one player record failed to load; it self-repaired from its own
backup after confirming and restarting. A texture/material pak has no write path

across the Fedora and Windows installs.

**Rules going forward:**

- Consider disabling Steam Cloud for Windrose while two machines share saves.
- Take a save snapshot before a test session that will involve several restarts.
